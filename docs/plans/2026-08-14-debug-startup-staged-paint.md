# Debug: 시작할 때 화면이 세 단계로 나뉘어 그려진다

## Symptom

앱을 실행하면 화면이 한 번에 나타나지 않고 세 단계로 채워진다(사용자 보고 2026-08-14).

1. 빈 화면이 먼저 보이고
2. 깜빡이면서 분할 레이아웃과 탭이 나타나고
3. 다시 깜빡이면서 파일 목록이 채워진다

2026-08-13의 `debug-startup-flash`(흰 사각형)와는 **다른 결함**이다. 그때는 창이 표시되기
전 흰 바탕이 번쩍이는 것이었고, 이번은 창이 표시된 **뒤** 내용이 단계적으로 붙는 것이다.

## Reproduction

1. 창을 최대화한 상태로 앱을 종료한다(세션에 `window.maximized = true`).
2. 앱을 실행한다.
3. 창이 뜬 뒤 약 0.3초에 걸쳐 위 세 단계가 눈에 보인다.

계측은 앱 안에 임시 프로브(`src/probe_tmp.rs`, 조사 후 제거)를 심어 **프레임 로그와 창 상태를
같은 타임라인**에 남기는 방식으로 했다. 창 상태는 별도 스레드가 2ms 간격으로
`IsWindowVisible`·`IsZoomed`·`GetWindowRect`를 읽어 변화가 있을 때만 기록했다.
화면 캡처는 이 환경에서 다른 창이 항상 앞에 있어 쓸 수 없었다(z-order).

## Phase 2 — Hypotheses

- H1: 첫 프레임의 `logic`이 활성 뷰를 만들기 전에 지나가 폴더 열거가 한 프레임 늦게
  시작된다 — 예측: `pass=0`에는 열거 요청이 없고 `pass=1`에 몰려 있다 —
  검증: 프로브 로그 → **확정**(`pass=0`은 `view=false`, 열거 요청 6건 전부 `pass=1`)
- H2: 최대화 복원이 창을 리사이즈해 레이아웃이 다시 배치된다 — 예측: 창 표시 후
  `screen` 크기가 한 번 바뀐다 — 검증: 프로브 로그 → **확정**(1706x1066 → 1706x1018)
- H2-a: 크기가 바뀌는 이유는 시작 사각형이 최대화 후 크기와 다르기 때문 — 예측:
  넘긴 시작 사각형과 실제 창 크기가 어긋난다 — 검증: **확정**(2560x1528을 넘겼는데
  창은 2560x1600으로 떴다 — `pixels_per_point=1.5`를 곱하면 3840x2292가 되어 화면 밖,
  OS가 화면 크기로 잘라 낸 값이 2560x1600이다)
- H3: 목록이 도착하기 전 빈 목록이 그대로 노출된다 — 예측: 읽는 중을 알리는 것이
  패널 위쪽 작은 줄뿐이고, 그마저 첫 프레임에는 열거가 시작되지 않아 뜨지 않는다 —
  검증: `ui::panel::show_content` 코드 확인 + 위 로그 → **확정**
- H4(기각): 2026-08-13의 흰 사각형이 남은 것 — 예측: 창 표시 전에 흰 바탕이 보인다 —
  검증: 창은 `vis=false`로 만들어져 첫 프레임을 그린 뒤 표시된다(4773 → 4842) → **기각**

## Phase 3 — Root Cause

세 가지가 겹쳐 세 단계가 된다.

**R1 — 열거가 한 프레임 늦게 시작된다.** 활성 워크스페이스의 뷰는 `ui`의
`ensure_active_view`에서 만들어지는데(D1), 폴더 열거를 거는 `panel.poll`은 그보다 **앞서
도는** `logic`에 있다. 첫 프레임의 `logic`은 뷰가 아직 없어 빈손으로 지나가고, 열거는 다음
프레임에야 시작된다. 그동안 창은 이미 표시돼 **빈 목록**이 보인다.

**R2 — 시작 사각형의 단위가 어긋났다.** `window_start::work_area_at`은 Win32
`MONITORINFO.rcWork`를 **물리 픽셀** 그대로 돌려주는데, 받는 쪽인
`ViewportBuilder::with_inner_size`·`with_position`은 **논리 픽셀**이다. 배율 150% 화면에서
작업 영역 2560x1528을 넘기면 winit은 그것을 논리로 읽어 물리 3840x2292 창을 만들려 하고,
화면을 넘으므로 OS가 화면 크기(2560x1600)로 잘라 낸다. 그 결과 창이 **작업 표시줄까지 덮는
크기**로 떴다가, 첫 프레임 뒤 최대화가 걸리는 순간 세로가 48논리픽셀 줄며 화면 전체가 다시
배치된다. 시작 사각형을 작업 영역에 맞춘 것은 크기가 튀지 않게 하려던 2026-08-13의 조치인데,
단위가 어긋나 그 목적이 무너져 있었다.

**R3 — 읽는 중이라는 것이 목록 자리에 보이지 않는다.** 읽는 동안 목록 본문은 그냥 비어
있고, 알림은 패널 위쪽 줄의 작은 스피너 하나뿐이다. 원격 탭에는 이미 자리표시 막대
(`remote_states::show_skeleton`)가 있는데 로컬 탭에는 없다.

**R4 — 어느 화면의 작업 영역인지도 같은 단위 혼선을 안고 있었다**(R2 수정 중 드러나 이어서
고침). `work_area_at(window.x, window.y)`에 넘기는 좌표는 세션에 저장된 **논리** 픽셀인데
`MonitorFromPoint`는 **물리** 좌표를 받는다. 배율 150%·화면 둘(물리 0~2559 / 2560~5119)이면
둘째 화면에 둔 창의 저장 좌표 1706이 물리 1706으로 읽혀 **첫째 화면**이 뽑힌다. 배율이
섞이지 않아도 100%만 아니면 걸리며, 창이 저장된 화면이 아닌 곳에서 열리거나(배율이 같을 때)
크기까지 어긋나 R2의 깜빡임이 되살아난다(배율이 다를 때). 화면이 하나면 어느 점을 찍어도
같은 화면이라 드러나지 않았다.

또한 판정을 **점 하나로 하면 배율이 다른 화면에서 모호하다**. 논리 x=960은 100% 화면에서는
물리 960이고 200% 화면에서는 물리 1920이라, 두 화면이 나란히 있으면 어느 쪽 점이든 상대
화면 안에 든다 — 처음 만든 중심점 판정이 이 때문에 옆 화면을 골랐다(시험이 잡았다).

**R5 — 화면 밖 구조가 창을 옆 화면에서 끌어왔다**(R4를 고친 뒤 실기에서 드러남).
`session::clamp_window`는 `viewport.monitor_size`, 즉 **창이 있는 화면 하나**의 크기만 알고
원점을 (0,0)으로 본다. 화면이 여럿이면 옆 화면 좌표(x=2700)는 그 크기(1706) 밖이라 늘
"화면 밖"으로 읽혀, 저장된 자리에 제대로 뜬 창이 곧바로 주 화면으로 끌려왔다. 게다가
**최대화 상태에서도** 저장된 일반 사각형으로 위치·크기 명령을 보내 방금 건 최대화까지
풀렸다(실측: 옆 화면에 최대화해 둔 창이 뜬 지 0.4초 만에 주 화면 306,166 1400x900이 됐다).

## Phase 4 — Fix

- Change:
  - `src/ui/app.rs` — `logic`이 패널을 폴링하기 **전에** 활성 뷰를 확보한다(R1).
    첫 프레임부터 열거가 시작되고, 그 프레임에 이미 `읽는 중…`이 뜬다.
  - `src/ui/window_start.rs` — 작업 영역을 그 화면의 배율로 나눈 **논리 픽셀**로 돌려준다(R2).
    물리→논리 변환은 순수 함수 `to_logical`로 떼어 시험한다.
  - `src/ui/window_start.rs` — 어느 화면인지는 `MonitorFromPoint`가 아니라 **화면 목록에서
    고른다**(R4). `EnumDisplayMonitors`로 화면마다 (전체 사각형·작업 영역·배율)을 모으고,
    화면마다 *"이 화면에 있었다면 물리 좌표가 얼마였겠는가"*(논리 × 그 화면의 배율)를 되짚어
    **창이 가장 온전히 드는 화면**을 고른다(`pick_monitor`·`coverage` — 순수 함수라 시험
    대상). 점 하나가 아니라 넓이 비율로 재는 이유는 배율이 다르면 한 점이 두 화면 모두에서
    말이 되기 때문이다. 화면 구성은 실행 사이에 바뀔 수 있어 목록을 저장하지 않고 시작할
    때마다 읽으며, 창이 있던 화면이 사라졌으면 **주 화면**으로, 화면을 하나도 못 읽으면
    저장된 사각형으로 물러선다.
  - `src/ui/window_start.rs`·`src/ui/app.rs`·`src/ui/session.rs` — 화면 밖 구조를 화면
    목록 기준으로 옮긴다(R5). 붙어 있는 화면 **전부**를 보고 창이 어디에도 넓이의 1/5조차
    걸치지 않을 때만 주 화면 작업 영역 안으로 당긴다(`rescue_offscreen`). **최대화
    상태에서는 아예 건드리지 않는다** — 저장된 사각형은 최대화를 풀었을 때 돌아갈 자리다.
    화면 하나만 보던 `session::clamp_window`는 이 함수로 대체돼 제거했고(호출부 1곳),
    그 시험 3건은 `clamp_into` 시험으로 옮겼다.
  - `Cargo.toml` — `GetDpiForMonitor`를 쓰기 위해 windows crate의 `Win32_UI_HiDpi`
    기능을 켠다(의존성 추가가 아니라 이미 쓰는 crate의 기능 하나).
  - `src/ui/panel.rs` — 목록이 아직 없는 채 읽는 중이면 목록 자리에 자리표시 막대를
    그린다(R3). 이미 목록이 있는 폴더에서 다른 폴더로 옮기는 중이면 종전대로 이전 목록을
    유지한다 — 그 자리를 비우면 오히려 화면이 한 번 더 깜빡인다.
- Test added:
  - `src/ui/window_start.rs` — `to_logical` 시험 3건(배율 1.5·1.0·비정상 배율).
  - `src/ui/window_start.rs` — 화면 고르기 시험 7건(화면 하나 / 배율이 같은 두 화면 /
    배율이 다른 두 화면 / **두 화면 모두에서 말이 되는 경우** / 쓰던 화면이 사라짐 /
    화면을 못 읽음 / 하나에서 둘로 늘어남).
  - `src/ui/window_start.rs` — 화면 밖 구조 시험 5건(화면 밖 창을 당김 / 화면보다 큰 창을
    줄임 / 화면 크기를 모름 / 주 화면이 원점이 아닌 배치 / **옆 화면의 창은 끌어오지 않음**).
    앞의 셋은 옛 `session::clamp_window` 시험을 옮긴 것이다.
  - `src/ui/panel/tests.rs` — 읽는 중 자리표시 판정 시험 3건.
  - 프레임 순서(R1)와 창 형상(R2)의 시각 결과는 자동 시험 대상이 아니라 위 재현 절차와
    프로브 계측으로 확인한다.
  - 시험이 실제로 결함을 잡는지 두 번 확인했다 — 자리표시(R3)는 그리기 분기를 끄면
    실패했고, 화면 고르기(R4)는 배율 되짚기를 빼면 실패했다. 처음 쓴 R4 시험은 창을 화면
    **한가운데** 두어 옛 방식으로도 우연히 통과했으므로, 창을 화면 왼쪽에 붙인 배치로
    고쳐 판정이 실제로 갈리게 했다.
