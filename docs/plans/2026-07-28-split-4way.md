# 네 방향 분할 — 탭 스트립 분할 버튼

**PRD**: `docs/prd.md` (FR-1·FR-12를 2026-07-28에 갱신 — 사용자 승인)
**이전 작업**: `docs/plans/2026-07-26-egui-migration-part2.md` (egui 이식 완료)

## 요구 이해

> 원문: "1번 이미지처럼 구현되어 있는데 2번 이미지처럼 분할된 화면 오른쪽에 분할 버튼을 추가하고 클릭하면 3번 이미지처럼 분할 메뉴 표시해서 분할 할 수 있도록 수정"
> 첨부: 이미지1(현재 탭 스트립) · 이미지2(목표 — 각 패널 탭 스트립 우측 끝에 `◫` 버튼) · 이미지3(그 버튼의 드롭다운 — "오른쪽/왼쪽/위쪽/아래쪽 분할" + `Ctrl+Alt+방향키`)

이해한 요구:
1. **패널마다** 탭 스트립 오른쪽 끝에 분할 버튼을 둔다. 분할된 모든 패널에 각각 보인다(이미지2에서 세 패널 모두에 있음).
2. 그 버튼을 누르면 **네 방향 분할 메뉴**가 뜬다. 항목 문구와 단축키 표기는 이미지3 그대로: 오른쪽(`Ctrl+Alt+→`)·왼쪽(`Ctrl+Alt+←`)·위쪽(`Ctrl+Alt+↑`)·아래쪽(`Ctrl+Alt+↓`).
3. 지금은 새 패널이 **항상 오른쪽/아래**에만 생긴다 — 왼쪽·위쪽 배치를 새로 만들어야 한다.
4. 분할 대상은 **버튼을 누른 그 패널**이다(활성 패널이 아니라 — 버튼이 패널마다 있으므로).

## Goal

각 패널의 탭 스트립 오른쪽 끝 `◫` 버튼으로 그 패널을 **네 방향 중 원하는 쪽으로** 분할할 수 있다. 보기 메뉴와 단축키도 같은 네 방향으로 통일되고, 기존 `Ctrl+\`·`Ctrl+Shift+\`는 각각 오른쪽·아래쪽 분할로 계속 동작한다.

## Decisions

- **D1 (축과 배치를 나눈다)**: 레이아웃 순수 로직은 `SplitDir`(가로/세로) + `SplitPlace`(앞/뒤) 두 값을 받고, UI는 `SplitTo`(오른쪽/왼쪽/위쪽/아래쪽) 하나로 다룬 뒤 변환한다. 트리는 방향 개념이 없고 first/second만 있으므로, 4방향을 그대로 트리에 내리면 매 호출부에서 같은 변환을 반복하게 된다. *Source*: `src/app/layout.rs`의 `Node::Split{first, second}` 구조.
- **D2 (기존 `split`에 인자를 추가한다)**: `split_at` 같은 두 번째 메서드를 만들지 않는다. 메서드가 둘이면 다음 작업자가 어느 것을 쓸지 헷갈리고, 하나는 곧 쓰이지 않는 레거시가 된다. 호출부 20곳 중 18곳이 테스트라 기계적 치환이고, Rust는 시그니처를 바꾸면 모든 호출부가 컴파일 오류로 드러나 누락이 숨을 수 없다.
- **D3 (분할 대상은 버튼을 누른 패널)**: 활성 패널이 아니라 **그 버튼이 속한 패널**을 나눈다. 버튼이 패널마다 있으므로 누른 곳이 대상인 것이 자연스럽다. 메뉴 바·단축키는 종전대로 활성 패널이 대상이다.
- **D4 (기존 단축키 의미 유지)**: `Ctrl+\` = 오른쪽 분할, `Ctrl+Shift+\` = 아래쪽 분할. 지금 동작(새 패널이 오른쪽/아래)과 정확히 같아 사용자가 익힌 동작이 바뀌지 않는다. 여기에 `Ctrl+Alt+방향키` 4종을 더한다(PRD FR-12 갱신 반영).
- **D5 (팝업은 앱 팔레트)**: 이미지3의 파란 테두리는 참고 앱의 것이다. 이 앱은 고정 다크(FR-21)이므로 `ui.menu_button`이 내는 앱 팔레트 팝업을 그대로 쓴다. *Source*: `src/ui/theme.rs::apply_dark`, 메뉴 바가 이미 같은 팝업을 씀.
- **D6 (버튼은 스크롤 밖 고정)**: 탭이 많아 스트립이 가로 스크롤돼도 버튼은 오른쪽 끝에 남는다(이미지2의 배치). `Sides`로 좌(스크롤되는 탭들)/우(고정 버튼)를 나눈다.
- **D7 (`+`는 그대로 탭 영역에)**: 새 탭 버튼은 지금처럼 탭들 바로 뒤에 둔다(이미지2도 동일) — 우측 고정 영역에는 분할 버튼만 둔다.
- **D8 (아이콘은 직접 그린다)**: `◫`(U+25EB) 같은 글리프에 의존하지 않고 `painter`로 사각형 테두리 + 세로 중앙선을 그린다. 맑은 고딕에 그 글리프가 있는지 런타임 렌더 전에는 알 수 없고, 없으면 두부(□)로 보인다 — 폰트 유무를 구현 중에 확인해 대안을 고르는 분기 자체를 없앤다. 이미지2의 아이콘과 같은 모양이며 색은 팔레트 상수를 쓴다.

### T1. 레이아웃 트리에 배치 위치 도입 (Type C)

- **PRD**: FR-1(네 방향 배치)
- **Files**: `src/app/layout.rs`, `src/ui/app.rs`, `src/app/layout_host.rs`, `tests/layout_flow.rs`
- **Design**: ① 배치 — 순수 로직이므로 `app/layout.rs`에 둔다 ② 신규 심볼 — `pub enum SplitPlace { Before, After }`(새 리프를 first/second 중 어디에 둘지) / `LayoutTree::split(target, dir, place, area)` ③ 의존 방향 — `layout`은 아무것도 참조하지 않는다(기존과 동일), 호출부만 인자를 추가 ④ 비추상화 — 4방향 enum을 `layout`에 두지 않는다(트리는 방향을 모른다 — D1). 배치 전략 트레이트·빌더도 만들지 않는다
- **내용**: `split`에 `place` 인자를 추가하고, `Before`면 `first: 새 리프, second: 기존`으로 뒤집는다. 호출부 20곳을 전부 갱신한다 — `ui/app.rs`와 `layout_host.rs`는 기존 동작 유지를 위해 `SplitPlace::After`를 넘긴다. 테스트 18곳도 `After`로 채우고, **방향별 신규 테스트**를 더한다
- **Acceptance**:
  - `split(.., SplitPlace::Before, ..)`가 새 리프를 **first**에, `After`가 **second**에 넣는다 (트리 구조 단위 테스트)
  - `Before` 분할 후 세션 왕복(`to_state()` → `from_state()`)에서 **각 패널의 탭이 제자리에 남는다** — 세션은 패널 배열을 리프 walk 순서로 짝지으므로, 새 리프가 앞에 들어가도 짝이 밀리지 않아야 한다 (단위테스트)
  - `Before` 분할 결과를 `shape()` → `from_shape()`로 왕복해도 같은 구조가 나온다
  - 최소 크기 거부(`TooSmall`)·대상 없음(`NotFound`) 동작이 `place`와 무관하게 종전과 같다
  - `cargo test` 전체 통과 — 기존 테스트가 모두 `After`로 옮겨져 결과가 바뀌지 않는다
- **Edge Cases**: 마지막 하나 남은 패널을 `Before`로 분할 / 중첩 분할 안쪽 노드를 `Before`로 분할(부모 비율에 영향 없어야 함) / 공간이 최소 크기 미만이라 거부될 때 트리가 변형되지 않고 그대로인지 / `Before` 분할 후 그 패널을 닫으면 형제가 부모 자리로 승격되는지
- **Halt Forecast**: 없음 (순수 로직 + 기계적 호출부 갱신). `layout_host.rs`(Win32 잔존)가 삭제 대상이지만 지금은 컴파일되므로 함께 고친다 — 삭제는 별도 승인 사안이라 이번에 건드리지 않는다

### T2. 메뉴·단축키 네 방향화 (Type C)

- **PRD**: FR-1(진입점), FR-12(단축키)
- **Files**: `src/ui/menu.rs`, `src/ui/app.rs`
- **Design**: ① 배치 — 4방향 표현과 메뉴·단축키를 `ui/menu.rs`에 ② 신규 심볼 — `pub enum SplitTo { Right, Left, Down, Up }` + `SplitTo::to_layout(self) -> (SplitDir, SplitPlace)`(변환은 한 곳에만 — D1) / `Command::Split(SplitTo)`가 `SplitH`·`SplitV`를 대체 ③ 의존 방향 — `ui::menu`가 `app::layout`의 `SplitDir`·`SplitPlace`를 참조(이미 `ui`→`app` 단방향) ④ 비추상화 — 명령 디스패처·키 바인딩 설정 파일을 만들지 않는다. 기존 `shortcut_table()` 배열에 4줄을 더할 뿐이다(반환 배열 길이가 10 → 14로 바뀐다)
- **내용**: 보기 메뉴의 "좌우 분할/상하 분할"을 "오른쪽/왼쪽/위쪽/아래쪽 분할" 네 항목으로 바꾼다(문구·순서는 이미지3 그대로). 단축키 표에 `Ctrl+Alt+←/→/↑/↓`를 더하고, 기존 `Ctrl+\`→오른쪽·`Ctrl+Shift+\`→아래쪽으로 잇는다(D4). `apply_command`는 `Command::Split(to)`를 받아 `to.to_layout()`으로 변환해 `split_active`에 넘긴다
- **Acceptance**:
  - 보기 메뉴에 네 항목이 이미지3의 문구·순서로 보이고, 각각 그 방향으로 분할된다 (⏳ HUMAN-VERIFY — 문구·순서는 코드 대조, 화면은 사용자 확인)
  - 오른쪽 항목에 `Ctrl+Alt+→`, 왼쪽에 `Ctrl+Alt+←`, 위쪽에 `Ctrl+Alt+↑`, 아래쪽에 `Ctrl+Alt+↓`가 표기된다 (코드 대조 + ⏳ HUMAN-VERIFY)
  - `Ctrl+\`가 오른쪽 분할, `Ctrl+Shift+\`가 아래쪽 분할로 **종전과 같은 결과**를 낸다 (단축키 표 단위테스트 + ⏳ HUMAN-VERIFY)
  - 단축키 표에 같은 키 조합이 둘 이상 없다 (기존 중복 검사 테스트가 새 항목까지 덮는다)
  - `SplitTo::to_layout`의 네 방향 매핑을 단위 테스트로 고정한다 (오른쪽=가로·After, 왼쪽=가로·Before, 아래=세로·After, 위=세로·Before)
  - 주소창·이름 편집에 포커스가 있으면 `Ctrl+Alt+방향키`가 텍스트 입력을 가로채지 않는다 (기존 포커스 가드가 그대로 적용됨을 확인)
- **Edge Cases**: `Ctrl+Alt+방향키`가 OS·다른 앱에 선점된 경우(동작 안 해도 앱은 정상) / 일부 키보드 레이아웃에서 `Ctrl+Alt`가 AltGr로 잡히는 경우 — **확인 결과 위험 낮음**: 대상 플랫폼의 한국어 레이아웃에는 AltGr가 없고, 방향키는 문자 입력이 아니며, `poll_shortcuts`의 포커스 가드가 텍스트 입력 중에는 단축키를 아예 보지 않는다 / 공간이 부족해 분할이 거부될 때 메뉴·단축키 모두 조용히 무시(현행과 동일)

### T3. 탭 스트립 분할 버튼·팝업 (Type D)

- **PRD**: FR-1(진입점 — 탭 스트립 분할 버튼)
- **Files**: `src/ui/tabs.rs`, `src/ui/panel.rs`, `src/ui/splitter.rs`, `src/ui/app.rs`
- **Design**: ① 배치 — 버튼·팝업 그리기는 `ui/tabs.rs`(탭 스트립의 일부), 요청을 위로 올리는 배선은 `panel`→`splitter`→`app` ② 신규 심볼 — `ui::tabs::TabStripOutcome { tab: Option<TabAction>, split: Option<SplitTo> }` / `ui::panel::PanelOutcome { menu: Option<MenuRequest>, split: Option<SplitTo> }` / `ui::splitter::LayoutOutcome { menu: Option<MenuRequest>, split: Option<(PanelId, SplitTo)> }` / `WorkspaceView::split_panel(&mut self, id: PanelId, dir, place, area)` — 기존 `split_active`는 활성 패널 전용이라 특정 패널을 대상으로 하는 경로가 따로 필요하다(`split_active`는 이것을 활성 id로 부르는 얇은 래퍼가 된다) ③ 의존 방향 — 아래에서 위로 값만 올라간다(콜백 없음 — 기존 `MenuRequest` 방식과 동일) ④ 비추상화 — 범용 툴바·액션 버스를 만들지 않는다. 반환 구조체 3개는 각 계층이 자기 것만 담는다
- **내용**: 탭 스트립을 `Sides`로 나눠 좌측은 기존 `ScrollArea`(탭들 + `+`), 우측은 고정 분할 버튼을 둔다. 버튼은 `ui.menu_button`으로 네 방향 팝업을 낸다(문구·단축키 표기는 T2의 메뉴와 같은 문자열). 요청은 `PanelId`와 함께 앱까지 올라가고, `ExplorerApp`이 **그 패널**을 대상으로 분할한다(D3)
- **Acceptance**:
  - 각 패널 탭 스트립 **오른쪽 끝**에 분할 버튼이 보인다 (분할된 모든 패널에 각각) — ⏳ HUMAN-VERIFY

  - 버튼을 누르면 네 항목 팝업이 뜨고, 문구·순서·단축키 표기가 보기 메뉴와 같다 — ⏳ HUMAN-VERIFY
  - **(단위테스트)** `WorkspaceView::split_panel`을 **비활성 패널의 id**로 호출하면 활성 패널이 아니라 **그 id의 패널**이 나뉜다 — 활성 id와 무관함을 고정한다. `split_active`로 잘못 구현하면 이 테스트가 깨진다
  - 팝업에서 방향을 고르면 그 패널이 그 방향으로 나뉜다 — ⏳ HUMAN-VERIFY (보조 확인). **판별 가능한 배치**: 위/아래로 나눈 뒤 **위 패널**의 분할 버튼을 눌러 팝업이 아래 패널 영역까지 내려오게 하고, 그 상태에서 항목을 클릭한다. 버튼을 누르는 순간 그 패널이 활성이 되므로(`splitter.rs`가 누른 좌표의 패널을 활성으로 삼는다) 이 배치가 아니면 활성 전환과 구분되지 않는다
  - 팝업 배경이 앱 다크 팔레트를 따른다 (메뉴 바 팝업과 같은 모양) — ⏳ HUMAN-VERIFY
  - 분할 후 새 패널이 활성이 된다 **(단위테스트)** — 기존 패널의 탭·목록 유지는 ⏳ HUMAN-VERIFY
  - `cargo build`·`cargo test`·`cargo clippy --all-targets -- -D warnings`·`cargo fmt --check` 통과
- **Edge Cases**: 탭 스트립 폭이 좁아 버튼과 탭이 겹칠 때 — `Sides::shrink_left`가 우측 버튼 폭을 먼저 확보하고 좌측을 남는 폭으로 **제한**하므로 겹침 자체가 생기지 않는다. 설령 좁아져도 좌측 `ScrollArea`의 클립이 탭을 잘라 버튼 자리를 침범하지 않는다(등록 순서가 아니라 **클립**이 근거다 — 등록 순서로 보면 나중에 등록되는 탭이 이긴다) / 팝업을 연 채 그 패널을 닫는 경우 / 공간 부족으로 분할이 거부될 때 팝업만 닫히고 아무 일도 없음 / 한 프레임에 두 패널의 팝업이 동시에 열리는 경우(egui가 하나만 유지) 
- **Halt Forecast**: `Sides`가 `ScrollArea`와 함께 쓰일 때 좌측 폭 계산이 어긋나 탭이 잘리면 → `Sides` 대신 우측 버튼을 먼저 `allocate`하고 남은 rect에 `ScrollArea`를 그리는 방식으로 전환(설계 대안, 승인 불요)

  - **D3(버튼이 속한 패널이 대상)는 수동 확인으로는 검증되지 않는다** — `splitter.rs`가 누른 좌표의 패널을 활성으로 만들기 때문에, `split_active`로 잘못 구현해도 화면에서는 같아 보인다. 비활성 id로 `split_panel`을 부르는 단위테스트가 이 계약을 잡는다.
