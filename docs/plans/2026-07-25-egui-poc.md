# egui(eframe) 이식 가능성 PoC

> PRD 연결 없음(의도적) — 사유는 `## PRD Coverage` 참조.

## 요구 이해

> 원문: "egui로 적용해줘" → 범위 확인 결과 **"PoC 먼저"** + **"Win32 셸 메뉴 유지"** 선택.
> 판정 기준은 **현행 NFR 그대로**, 의존성은 **feature 게이트**로 격리.

이해한 요구:
1. UI 프레임워크를 egui(eframe)로 옮길 수 있는지를 **실측으로 판단할 근거**를 만든다. 전면 이식은 이 PoC 결과를 보고 별도 계획으로 결정한다.
2. PoC는 **별도 바이너리**이며 기존 Win32 앱(`src/main.rs`·`app`·`panel`)의 **동작을 바꾸지 않는다**.
3. 검증 대상은 셋: ① 대량 항목 가상 스크롤 성능 ② 시스템 아이콘 표시 ③ Win32 셸 컨텍스트 메뉴 연동.
4. 성공·실패는 현행 NFR-1(콜드 스타트 1초)·NFR-2(유휴 메모리 50MB)·NFR-3(10만 파일 무정지)로 측정하되, **미달해도 자동 기각하지 않고 실측값을 보고**해 사용자가 판단한다.
5. egui 의존성은 기본 빌드에 섞이지 않게 feature로 격리한다.

## Goal

`cargo run --bin egui_poc --features egui-poc`로 뜨는 단일 패널 파일 목록 창을 만들어, 위 3항목이 egui에서 **실제로 되는지**와 성능·메모리 실측값을 확보한다. 산출물은 동작하는 PoC 바이너리 + 측정 결과 기록.

## Decisions

- **D1 (의존성 격리)**: `optional = true` + `[features] egui-poc` + `[[bin]] required-features`. 기본 `cargo build`는 egui를 컴파일하지 않는다. Source: 사용자 선택(feature 게이트).
- **D2 (PoC 파일 구조)**: `src/bin/egui_poc/` 디렉터리 — `main.rs`(앱·테이블), `icon_tex.rs`(아이콘→텍스처), `shell_host.rs`(HWND·서브클래스·셸 메뉴). Cargo `[[bin]] path`로 명시. Source: AGENTS "파일은 하나의 명확한 책임".
- **D3 ("무변경"의 해석)**: 기존 앱은 **동작·시그니처 무변경**을 뜻한다. `format_size_kb`/`format_filetime`의 `pub(crate)` 승격은 동작에 영향이 없어 허용 범위로 본다(사전 승인 항목에 등재). 그 외 기존 코드는 손대지 않는다.
- **D4 (렌더 백엔드)**: eframe 기본값(wgpu)으로 측정하되, **T5에서 `glow`도 함께 측정**했다(`--glow` 인자). 원래는 "wgpu 실패 시에만 glow"였으나, wgpu 메모리가 NFR-2를 7배 초과해 **원인이 백엔드인지 egui인지 가르지 않으면 결론이 무의미**해지기 때문이다. 결과적으로 백엔드가 메모리를 2.7배 갈랐다(Deferred에 있던 비교 항목을 앞당겨 수행).
- **D5 (COM 초기화)**: UI 스레드에서 `CoInitializeEx(APARTMENTTHREADED)`를 호출하되 **반환을 세 갈래로 처리**한다 — `S_OK`(이번에 초기화)·`S_FALSE`(이미 초기화됨, eframe/winit이 먼저 초기화했을 수 있음) 모두 **정상 진행**, `RPC_E_CHANGED_MODE`(다른 아파트먼트로 이미 초기화됨)면 셸 메뉴가 STA를 요구하므로 **T4를 실패 판정하고 보고**한다(임의 우회 금지). 어느 경우인지는 실행해 봐야 알 수 있으므로 세 분기를 모두 구현한다 — 이 선택은 실제 반환값과 무관하게 성립한다.
- **D6 (아이콘 크기)**: 16px 스몰 아이콘(`IconCache`가 `SHGFI_SMALLICON` 기반). 고DPI 환경에서의 표시 화질은 T5에서 육안 관찰해 기록한다(확대 처리 방식은 실행 결과로 확인).
- **D10 (측정 수단 — T2 구현 중 추가)**: acceptance를 실측하려면 조작 자동화가 필요해 다음을 넣었다. 모두 PoC 전용 계측이며 제품 기능이 아니다.
  - **시작 폴더 인자**(`egui_poc <경로>`) — 주소 입력 UI 없이 대량 폴더에 바로 진입.
  - **`--bench`** — 매 프레임 `vertical_scroll_offset`을 왕복시키며 렌더 시간 표본(평균·p95·최대)을 모은다. 사람이 휠을 돌리는 방식은 재현되지 않아 수치가 나오지 않는다.
  - **F5 새로고침** — 창이 이미 떠 있는 상태의 열거 응답성을 재는 유일한 경로(첫 로드는 창 표시 파이프라인과 겹쳐 측정이 왜곡된다).
  - **로드 계측·스피너** — "열거 중 몇 프레임을 그렸는가"를 표시. 스피너는 애니메이션이라 매 프레임 리페인트를 유발해 응답성이 눈에 보인다.
  - **첫 프레임 뒤 로드**(`deferred_start`) — 생성자에서 바로 열거하면 창이 늦게 뜨고 응답성이 측정되지 않는다.
- **D9 (열거 스레드)**: 폴더 열거는 `enumerate_dir`을 **자체 워커 스레드 + `std::sync::mpsc` 채널**로 감싸고 `ctx.request_repaint()`로 UI를 깨운다. 기존 `spawn_enumerate`는 완료를 HWND로 통지해 egui에서 쓸 수 없다(Investigation Log). UI 스레드 동기 열거는 10만 파일에서 창이 멈춰 **NFR-3 판정을 왜곡**하므로 쓰지 않는다(기존 앱과 같은 조건으로 비교). Source: `src/fs/enumerate.rs:60-100`, AGENTS.md "UI 스레드에서 블로킹 I/O 금지".
- **D7 (정렬)**: 폴더 우선 + 이름 오름차순 고정. 열 클릭 정렬은 PoC 검증 목표가 아니므로 넣지 않는다(Deferred).
- **D8 (탐색 범위)**: 대량 폴더 도달을 위해 **더블클릭 진입 + 상위(↑) + 경로 표시**만 넣는다. 히스토리·탭·트리·주소 입력은 제외(Out of Scope).

### T1. 의존성·바이너리 스캐폴드 (Type C)

- **Files**: `Cargo.toml`, `src/bin/egui_poc/main.rs`(신규)
- **Design**: ① 배치 — bin 타깃 `src/bin/egui_poc/main.rs`, 기존 lib 재수출(`file_explorer::fs`)을 사용 ② 신규 심볼 — `PocApp`(eframe::App 구현, 현재 폴더·항목 목록 보유) / `install_korean_font(&egui::Context)`(맑은 고딕 로드) ③ 의존 방향 — PoC → lib(fs) 단방향, lib은 PoC를 모른다 ④ 비추상화 — UI 추상 레이어·트레이트 없이 eframe::App 하나로 직접 구현(PoC이므로 재사용 구조를 만들지 않는다)
- **내용**: optional 의존성 + feature + `[[bin]]` 설정, eframe 창 기동, 다크 비주얼(`egui::Visuals::dark`), 한글 폰트 설치, COM STA 초기화(D5)
- **Acceptance**:
  - `cargo run --bin egui_poc --features egui-poc` → 창이 뜨고 한글 문자열이 두부(□) 없이 표시된다
  - `cargo build`(기본 feature)의 컴파일 대상에 eframe이 **포함되지 않는다**(`cargo build -v`로 확인 또는 `cargo tree -e normal`에 미출현)
  - `cargo clippy --all-targets --features egui-poc -- -D warnings` 경고 0
- **Edge Cases**: 폰트 파일 부재(다른 Windows 구성) → 기본 폰트로 폴백하고 경고 로그 / COM 초기화 반환값 3분기(D5)
- **Halt Forecast**: 의존성 추가(→ 사전 승인) / wgpu 초기화 실패(→ D4에 따라 glow 전환 후 계속)

### T2. 파일 목록 가상 스크롤 테이블 (Type C)

- **Files**: `src/bin/egui_poc/main.rs`, `src/panel/file_list.rs`(가시성 승격 2줄)
- **Design**: ① 배치 — `main.rs` 내 `PocApp::table_ui` ② 신규 심볼 — `PocApp::load_dir(&Path)`(워커 스레드 열거 시작, 세대 번호 증가), `PocApp::poll_enum(&egui::Context)`(채널 수신→정렬→보관), `sort_entries(&mut Vec<FileEntry>)`(폴더 우선·이름) ③ 의존 방향 — `fs::enumerate::enumerate_dir`·`panel::file_list`의 포맷 함수 참조 ④ 비추상화 — 정렬 키 추상화(SortKey 유사)·뷰모델 계층 없이 `Vec<FileEntry>` 직접 사용
- **내용**: `TableBuilder` 4열(이름·크기·종류·수정일) + `body.rows(row_h, total, ..)` 가상 렌더. 열거는 워커 스레드(D9). 더블클릭 폴더 진입, ↑ 상위 이동, 상단에 현재 경로·항목 수·상태(열거 중/완료) 표시. 프레임 시간(ms)을 창 상단에 표시해 스크롤 부하를 눈으로 확인
- **Acceptance**:
  - 10만 개 파일 폴더에서 스크롤 시 **프레임 시간이 16ms 내외를 유지**하고 멈춤이 없다(표시된 수치로 판정)
  - 열거 중에도 **창이 응답한다**(스피너/상태 문구가 갱신되고 창 이동·크기 조절이 가능)
  - 4개 열이 표시되고 크기·수정일 문자열이 기존 앱과 **같은 형식**이다(`1,206 KB`, `2026-07-25 09:30`)
  - 폴더 더블클릭 진입·상위 이동이 동작한다
- **실측 결과 (debug 빌드, 10만 파일 폴더)**:
  - 스크롤 벤치 721프레임 — **평균 8.88 ms · p95 10.55 ms · 최대 39.75 ms** (16ms 기준 충족, 가상 스크롤 동작 확인)
  - F5 재열거 — **로드 115 ms 동안 11프레임 렌더** (열거 중 UI 응답 확인). 첫 로드(589ms/1프레임)는 창 표시 파이프라인과 겹쳐 측정 불가라 F5로 분리 측정했다
  - 4열·형식 일치 확인(`0 KB`, `2026-07-25 10:21`), 상위 이동 확인(`egui_poc_100k` → `Temp`, 516개 항목)
  - ⏳ **HUMAN-VERIFY — 폴더 더블클릭 진입**: 코드 경로는 구현(행 4개 셀 Response를 union해 `double_clicked()` 판정)했고 단일 클릭(상위 버튼)은 자동 주입으로 확인했으나, **더블클릭 자동 주입이 egui에 인식되지 않아** 실측하지 못했다. 수동 확인 필요
- **Edge Cases**: 빈 폴더(행 0) / 접근 거부 폴더(`EnumOutcome` 실패 분기 → 목록 비우고 사유 표시) / 260자 초과 경로·유니코드 파일명 / 항목 0일 때 `rows(_, 0, _)` 호출 / **취소** — 열거 중 다른 폴더로 이동하면 **세대 번호가 다른 늦은 결과를 폐기**(기존 앱의 `generation` 방식과 동일) / 워커 결과 수신 전 앱 종료(채널 송신 실패는 무해하게 무시)
- **Halt Forecast**: `file_list.rs` 가시성 승격(→ 사전 승인) / 10만 파일 테스트 폴더 생성(→ 사전 승인, 시스템 임시 폴더·측정 후 삭제)

### T3. 시스템 아이콘 텍스처 (Type C)

- **Files**: `src/bin/egui_poc/icon_tex.rs`(신규), `src/bin/egui_poc/main.rs`
- **Design**: ① 배치 — 변환·캐시를 `icon_tex.rs`에 격리(unsafe 집중) ② 신규 심볼 — `IconTextures`(이미지 리스트 인덱스 → `egui::TextureHandle` 맵), `IconTextures::get(&mut self, ctx, himl, index) -> TextureHandle`, 내부 `icon_to_rgba(HICON) -> Option<ColorImage>` ③ 의존 방향 — `fs::icons::IconCache`에서 인덱스만 받아 변환, IconCache는 수정하지 않는다 ④ 비추상화 — 아이콘 소스 추상 트레이트 없이 Win32 경로 하나만 구현
- **내용**: `ImageList_GetIcon` → `GetIconInfo` → `GetObjectW`/`GetDIBits`로 32bpp BGRA 추출 → 채널 순서를 RGBA로 변환 → `ColorImage` → `ctx.load_texture`. 알파 합성 방식(스트레이트/프리멀티플라이)은 **실제 픽셀 값으로 판정해 선택**한다 — 어느 쪽이든 표시 방식만 달라질 뿐 task 성립에는 영향이 없다. HICON·HBITMAP은 즉시 해제. 인덱스별 캐시로 재사용
- **Acceptance**:
  - 폴더·`.exe`·`.txt`·`.png` 항목이 **각각 다른 시스템 아이콘**으로 표시된다(Windows 탐색기와 육안 대조)
  - 같은 확장자 행을 수백 개 스크롤해도 텍스처 생성 횟수가 **아이콘 종류 수만큼**만 늘어난다(카운터를 화면에 표시)
  - GDI 핸들 누수 없음 — 10만 파일 스크롤 후 프로세스 GDI 개체 수가 안정적(작업 관리자 'GDI 개체' 열로 확인)
- **Edge Cases**: `ImageList_GetIcon` 실패(null HICON) → 빈 텍스처·아이콘 생략 / 마스크만 있는 1bpp 아이콘(알파 없음) → 마스크 기반 폴백 또는 불투명 처리 / 인덱스 −1
- **실측 결과 (debug 빌드)**:
  - `C:\Windows` — 폴더 아이콘 정상 표시, 텍스처 **1개**(종류가 하나뿐)
  - `C:\Windows\System32` (4952개 항목) — `.dll`·`.exe`가 각각 다른 시스템 아이콘으로 표시, 텍스처 **197개**(= 아이콘 종류 수, 항목 수와 무관 → 캐시 동작)
  - **GDI 개체 60 → 60** (벤치 스크롤 12초 후에도 불변 — 누수 없음, `GetGuiResources`로 측정)
  - 아이콘이 붙은 상태의 스크롤 벤치(811프레임): 평균 12.23 ms · p95 16.99 ms · 최대 45.51 ms
  - ⚠️ 렌더 최대 **3096 ms** 스파이크 1회 관측 — 텍스처 다수가 한 프레임에 생성될 때 발생. 실제 이식 시 프레임당 생성 수 제한이 필요하다(Deferred 등록)
- **Halt Forecast**: 알파 채널이 전부 0으로 나오는 경우(아이콘 종류에 따라 발생) → 마스크(`hbmMask`) 기반 알파 합성으로 대응, 그래도 안 되면 실패로 보고(임의 우회 금지)

### T4. Win32 셸 컨텍스트 메뉴 연동 (Type D)

- **Files**: `src/bin/egui_poc/shell_host.rs`(신규), `src/bin/egui_poc/main.rs`
- **Design**: ① 배치 — HWND 획득·서브클래스·메뉴 호출을 `shell_host.rs`에 격리 ② 신규 심볼 — `ShellHost { hwnd: HWND }`, `ShellHost::new(&eframe::CreationContext) -> Option<ShellHost>`(raw-window-handle 0.6로 HWND 추출 후 `SetWindowSubclass` 설치), `ShellHost::popup(&self, folder: &Path, items: &[PathBuf], screen_pos: (i32,i32))`, 서브클래스 프로시저 `poc_shell_proc`(→ `forward_menu_msg` 위임) ③ 의존 방향 — `fs::shell_menu` 재사용, 역참조 없음 ④ 비추상화 — 플랫폼 추상 트레이트 없이 Windows 전용 구현
- **내용**: `CreationContext::window_handle()`에서 `RawWindowHandle::Win32` → HWND. 서브클래스에서 `forward_menu_msg(msg, w, l)`가 `Some`이면 그 값을 반환(서브메뉴 동적 채움), 아니면 `DefSubclassProc`. egui에서 우클릭 감지 시 **화면 좌표**로 변환해 `show_context_menu` 호출(모달 루프 동안 egui 프레임은 멈춤 — 정상 동작으로 간주)
- **Acceptance**:
  - 파일 행 우클릭 → **Windows 셸 메뉴가 표시**되고 "속성"이 실제로 열린다
  - "보내기" 등 **서브메뉴가 펼쳐진다**(= `forward_menu_msg` 포워딩 동작 확인, 서브클래스 미설치 시 빈 서브메뉴가 나오므로 구분 가능)
  - 빈 영역 우클릭 → 폴더 배경 메뉴("새로 만들기" 포함)가 표시된다
  - 메뉴를 닫은 뒤 egui 창이 정상 갱신되고 입력이 계속 동작한다
- **Edge Cases**: HWND 획득 실패(headless·다른 백엔드) → 셸 메뉴 비활성 + 화면에 사유 표시 / 다중 선택 없음(PoC는 단일 선택) / 메뉴 모달 중 창 크기 변경 / 메뉴 표시 중 대상 파일 삭제(기존 코드가 조용히 무시)
- **실측 결과 — 부분 충족**:
  - ✅ **Win32 셸 메뉴가 egui 창에서 뜬다** — `CreationContext::window_handle()`로 HWND 획득, `SetWindowSubclass` 설치, `TrackPopupMenuEx` 모달 표시까지 동작. "새로 만들기·속성·액세스 권한 부여" 등 실제 셸 항목이 표시됐다(`t4_menu.png`). COM은 `S_OK`로 STA 확보
  - ✅ 메뉴를 닫은 뒤 앱이 계속 정상 동작(이후 프레임 렌더·측정 표시 갱신 확인)
  - ❌ **파일 행 우클릭 → 항목 대상 메뉴**: 미충족. 뜬 메뉴는 모두 **배경 메뉴** 경로였다
  - ❌ **서브메뉴 펼침(`forward_menu_msg` 포워딩) 실측**: 행 메뉴에 도달하지 못해 확인 못 함
  - **원인**: `egui_extras` 테이블 **행의 클릭 이벤트가 잡히지 않는다**. `TableBuilder::sense(Sense::click())`(기본값은 `hover`)을 켜고, 셀 Response를 `union`하고, 마지막 열까지 좌표를 바꿔가며 4회 시도했으나 `secondary_clicked()`·`double_clicked()`가 모두 false였다. **Win32 연동 문제가 아니라 egui_extras 입력 처리 문제**다(T2의 더블클릭 미검증과 같은 뿌리)
- **Halt Forecast**: `RPC_E_CHANGED_MODE`로 STA 확보 실패(D5) → T4 실패 판정 후 보고 / winit이 창을 재생성해 HWND가 무효화되는 경우 → 매 프레임 재확인 방식으로 전환

**결론 (이식 손익)**
1. **기술적으로는 이식 가능하다** — 가상 스크롤 성능·시스템 아이콘·Win32 셸 메뉴 호출이 모두 실제로 동작했다.
2. **대가는 메모리와 배포 크기다** — glow 백엔드로도 131MB(현행 22MB의 6배)라 NFR-2를 충족할 수 없고, exe는 0.42MB → 10MB가 된다. **wgpu 기본값을 쓰면 359MB로 더 나쁘다**(백엔드 선택이 메모리를 2.7배 가른다).
3. **미해결 리스크가 하나 남았다** — egui_extras 테이블의 행 클릭 이벤트가 잡히지 않아, 해결하지 못하면 목록 UI를 직접 구현해야 하고 이식 비용이 크게 늘어난다.
